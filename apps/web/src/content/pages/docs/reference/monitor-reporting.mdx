A reporting is a named availability commitment: a monthly uptime target applied to a set of monitors. openstatus judges every monitor in the reporting on its own, month by month, and seals each month once it is over, so the result you show a customer no longer changes.

Find them in the dashboard under [**Reportings > Monitors**](https://app.openstatus.dev/reportings/monitors). Reportings are included in the Pro and Scale plans.

## Properties

| Property | Description |
|---|---|
| Name | Required. Shown in the list, the reporting page, the export and the email. |
| Monthly uptime target | A percentage with up to three decimals, for example `99.9`. Presets: `99`, `99.5`, `99.9`, `99.95`, `99.99`. The form shows how much downtime the target allows in a 30-day month. One target per reporting, the same for every monitor in it. |
| Count slow responses as downtime | Off by default. See [strict mode](#strict-mode). |
| Time zone | `UTC` by default. The zone the reporting's months start and end in. It can be changed only until the first month is sealed. |
| Monitors | The monitors the reporting covers. A monitor can be in several reportings. |

Owners and admins can create, edit, archive and delete reportings, and add or remove [excused windows](#excused-windows). Every workspace member can view them and download the export. Each change is recorded in the audit log, with the values before and after an edit.

Reportings are managed in the dashboard only. They are not available over the API, the CLI or the MCP server.

### Eligible monitors

A reporting judges run verdicts (see [method](#method)), so it accepts only monitors that produce them:

- **Accepted:** [HTTP](/docs/reference/http-monitor), [TCP](/docs/reference/tcp-monitor), [DNS](/docs/reference/dns-monitor), [ICMP](/docs/reference/icmp-monitor) and [gRPC](/docs/reference/grpc-monitor) monitors that check from at least one cloud region.
- **Rejected:** heartbeat monitors, and monitors that run from [private locations](/docs/reference/private-location) only. The form names the monitor and the reason.

## What is judged

One monitor, one calendar month in the reporting's time zone. There is no combined figure across a reporting's monitors: a reporting with three monitors produces three results per month, each met or missed against the same target.

Months start and end at local midnight in the reporting's [time zone](#properties), on the page, in the export, when sealed and in the email. With the default `UTC`, a failed run at 23:30 UTC on October 31 belongs to October.

### Method

The figure weighs **time**, not requests. A run is one scheduled check of a monitor, carried out by every cloud region the monitor is set to. Each run gets one verdict from the regions that reported it:

| Verdict | When |
|---|---|
| Failed | At least half of the reporting regions failed. |
| Slow | Not failed, and at least half of the reporting regions were slow or failed. |
| OK | Otherwise. |

So one slow or failing region out of three is a normal run. Choosing the regions is up to you: regions close to your users make the majority mean something.

A verdict stands until the next run, so each run weighs the time up to the next one, and a change of check frequency mid-month changes nothing. When the gap between two runs is more than twice the longer of the gaps before and after it, the earlier verdict covers only that longer gap and the rest of the gap is **unmeasured**. The time before the first run and after the last follow the same rule. Unmeasured time is neither up nor down: paused monitors, [paused checks during a maintenance](#maintenance) and scheduler outages leave the month instead of counting against it. **Coverage** is the share of the month's non-excused time that was measured.

On-demand checks and private locations never count. They are requests outside the schedule, or outside the cloud regions.

### Monthly uptime

```
measured = OK time + slow time + failed time      (excused time cut out)
down     = failed time + slow time                in strict mode
down     = failed time                            otherwise
uptime   = (measured − down) / measured
```

Excused time is the time inside the reporting's [excused windows](#excused-windows), cut out at the millisecond. It drops from both sides of the fraction.

- A month is **met** when its uptime is at or above the target. A month exactly at the target is met. The comparison is exact, on whole milliseconds.
- Uptime is shown with three decimals, **rounded down**, so a missed month never displays as its target.
- A month without measured time has no judgement. It shows an em dash (`—`): never 100%, never a miss. The same holds for a month whose time was all excused.

### Strict mode

With **Count slow responses as downtime** on, slow time counts as down instead of up. A check is slow when it takes longer than its own monitor's degraded threshold (for example the HTTP monitor's [degraded](/docs/reference/http-monitor#degraded) setting), as recorded when it ran. A monitor without a degraded threshold is never slow, so strict mode changes nothing for it; the form flags such monitors.

## Month states

The reporting page shows a table of its monitors against the last 12 or 24 months, plus the running month. Each cell is in one of these states, the first that applies:

| State | When | Figures from | Target and strict mode |
|---|---|---|---|
| Sealed | The month was sealed for this monitor and reporting. | The counts stored at sealing. | The ones stored at sealing. |
| Preview | The previous month, over and not sealed yet (at most 45 days after it began). | Its checks. | The ones that will seal it. |
| Live, provisional | The running month. | Its checks so far. | The ones in effect this month. |
| None | Any other month: before the reporting or the monitor's membership, or never sealed. | — | — |

- Sealed cells are filled; preview cells have a dashed border; live cells use a distinct tone. Hover a sealed cell for its seal date and stored terms.
- Months are only judged from their own checks or their seal. A month older than the previous one that was never sealed has no figure.
- A live month below target is a miss in progress, not a result. If recent counts cannot be loaded, the page still renders and says the recent weeks may be incomplete.

### Month detail

Select any month cell to open that monitor's month in a side sheet. The month is kept in the address (`?monitor=…&month=YYYY-MM`), so a link opens the same month. Cells without data cannot be opened.

| Part | Shows |
|---|---|
| Uptime | The month's figure and its coverage. A live month reads **So far**. |
| Budget left | The downtime the target allows in the month minus the time already counted as down. Negative once the month is over budget. |
| Budget left by day | A chart of the budget left at the end of each day, against an even burn from the full budget to zero, with each day's down and slow time as bars underneath. Where the budget ran out, a marker names the moment. A live month projects its current pace to the end of the month. |
| What used the budget | Every down, slow, unmeasured and excused stretch of the month, newest first, with how it was treated: counted, counted as up, excused or not measured. |
| Service credit | The month's [credit](#service-credits), when the reporting has a schedule. |

- The header says whether the month is sealed, a preview or live.
- Sealed months read from what was stored at sealing, so the detail of a month stays available after its checks expire.
- **Excuse a window** opens the [excused window](#excused-windows) dialog prefilled with the latest counted stretch. It is offered for the live and the preview month only, since older and sealed months are locked.

### Sealing

A task seals the previous month. For each monitor in a reporting it seals the month when all of these hold:

- At least 72 hours have passed since the month ended in the reporting's time zone, so a reporting can still be corrected or deleted. Checks are kept for 45 days, so a month not sealed within 45 days of its start is never sealed.
- The reporting, and the monitor's membership in it, both existed before the month ended. A reporting created on November 5 is first sealed for November, never for October.
- The month's checks load. If not, the next run tries again.
- The reporting is not archived, the monitor is not deleted and the workspace's plan includes reportings.

Sealing stores the measured, down, excused and unmeasured time, the run counts, the excused windows that applied, the target and the strict setting of that moment, and the month's episodes: down, slow, unmeasured and excused stretches. It never changes afterwards. A month whose time was all excused is sealed without a judgement and keeps its windows. A month that is still unsealed when it stops being the previous month shows no figure.

### Missed months

"The last 12 months" always means the twelve complete months before the current one.

- **Per monitor:** how many of those months it missed.
- **Per reporting:** how many of those months had at least one monitor miss. This is the number a "three missed months in twelve" clause reads.

Both count sealed and preview months, and say how many of the misses are previews. Live months never count. The reporting list shows the same twelve months as a strip per reporting: a month is missed when any monitor missed it, met when at least one monitor was judged and none missed, and empty otherwise.

When a sealed month misses its target, the workspace owners get one email per reporting and month, listing the monitors that missed and linking to the reporting.

## Excused windows

An excused window is a stretch of time whose runs count for no monitor in the reporting: a planned maintenance, an outage caused by the customer, a provider failure your contract excludes. Add one from the **Excused downtime** section of the reporting page with **Add window**.

| Field | Description |
|---|---|
| From, To | The window, at most 7 days long. Entered in your browser's timezone; the list shows windows in UTC. |
| Kind | `Maintenance`, `Emergency`, `Third party`, `Customer caused`, `Force majeure` or `Other`. A label for the record; it changes nothing in the calculation. |
| Reason | Required. Shown in the list and kept with the sealed month. |

- A window applies to every monitor in the reporting, including monitors added later.
- Runs inside it are left out of both sides of the month: neither up nor down.
- Overlapping windows excuse a run once.
- A window across a month boundary is split there. Each month drops only its own part.
- Windows can only be added or removed in the current and the previous month, and only while no month they touch is sealed. A sealed month records the windows that applied, so its figure never changes. Locked windows show a lock icon.
- The add dialog shows when the last window of the same kind started and how many of the last two complete months had a miss. It refuses nothing on that account: contract rules about which windows qualify, such as notice periods or weekly limits, are not checked.
- Adding and removing a window are recorded in the audit log.

## Service credits

A reporting can carry a credit schedule: the share of the monthly fees a customer gets back when a month misses its target. Add one under [**Service credits**](https://app.openstatus.dev/reportings/monitors) on the reporting's edit page with **Add a credit schedule**.

| Field | Description |
|---|---|
| Credit per step | Percent of fees credited for each step below the target, for example `3`. |
| Step below target | The size of one step in uptime percentage points, for example `0.25`. |
| Cap | The most a month can earn, in percent of fees, for example `100`. |

Each value is above 0 and at most 100, with up to three decimals. The card shows a worked example for the reporting's target.

```
shortfall = target − uptime                      (exact, not the rounded display)
steps     = shortfall / step, rounded up
credit    = min(steps × credit per step, cap)
```

- A started step counts as a full one. With a 99.5% target, 0.25 points per step and 3% per step, a month at 99.12% is 0.38 points short: 2 steps, a credit of 6%.
- A month at or above its target earns 0%. A month without a judgement earns nothing and shows an em dash.
- The shortfall is computed from the exact measured and down time, so a month whose uptime displays as `99.249` is judged on its real value.
- Credits are a percentage only. openstatus stores no fee or currency and shows no amount; what the percentage applies to is settled when you invoice it. It is a computed figure, not a billing action, and claims or payouts are not tracked.

The schedule is versioned with the target: adding, changing or removing it applies from the next month, and a sealed month keeps the schedule it was sealed with and the credit it earned. Months sealed before a schedule existed have no credit. The [month detail](#month-detail) shows the month's credit, labelled provisional for the live and the preview month, and the [export](#export) carries it.

Each monitor's month earns its own credit. openstatus does not yet add credits across a reporting's monitors, or add support credits to them under the cap.

### Support terms

Under [**Support terms**](https://app.openstatus.dev/reportings/monitors) on the edit page, **Use the incident policy** links the workspace's [incident reporting](/docs/reference/incident-management#reporting) to this reporting, so its [support credits](/docs/reference/incident-management#support-credits) belong to the same commitment.

- A workspace has one incident reporting, so only one monitor reporting can link it. The card names the reporting that holds the link, and saving a second link is refused with the same name.
- Turning the incident reporting off, or archiving the monitor reporting, removes the link. Both are recorded in the audit log.
- Support credits cover incidents declared in openstatus, not support requests tracked in another tool.

## Editing, archiving and deleting

- A new target, strict setting or credit schedule applies from the next month in the reporting's time zone. Sealed months keep the terms they were sealed with.
- Adding a monitor judges it from the moment it joined; earlier months show none.
- Removing a monitor keeps its sealed months. They are hidden until the monitor is added back.
- Deleting a monitor removes it from every reporting.
- A reporting without a sealed month can be deleted.
- A reporting with a sealed month can only be archived: it becomes read-only, seals no further months and leaves the default list. Its sealed months stay on record. The **Archived** tab still shows it.

## Export

The **Export** button on a reporting's page downloads its months as a CSV file, one row per monitor and month. This is the file to send to a customer or auditor.

- Pick a range of months. The default is the last 12 complete months; a file covers at most 60.
- Live months are left out unless you tick **Include live months**. They are then marked `live (provisional)`.
- The figures equal the ones on the page. Sealed rows carry the target and strict setting they were sealed with.

The first line states the method. The second says when the file was generated, which time zone the calendar months are in, that excused runs are left out of both sides, and that uptime is floored to three decimals. Then the columns:

| Column | Description |
|---|---|
| `reporting` | Reporting name. |
| `target` | Target in percent, for example `99.900`. |
| `strict` | `yes` or `no`. |
| `monitor_id`, `monitor_name`, `monitor_url` | The monitor. |
| `month` | `YYYY-MM`. |
| `state` | `sealed`, `preview`, `live (provisional)` or `none`. |
| `ok_runs`, `degraded_runs`, `failed_runs` | Run counts by verdict; slow runs are `degraded_runs`. |
| `excused_runs` | Runs inside the reporting's [excused windows](#excused-windows), left out of both sides of the uptime. `0` without windows. Empty without runs. |
| `uptime` | Percent, floored to three decimals. Empty without runs, or when every run was excused. |
| `met` | `yes`, `no`, or empty without runs or when every run was excused. |
| `sealed_at` | ISO timestamp, sealed rows only. |
| `method` | `time` or `runs`, see [method](#method). |
| `time_zone` | The zone the month is in. |
| `measured_ms`, `down_ms`, `excused_ms`, `unmeasured_ms` | Time in milliseconds, method `time` only. |
| `coverage` | Measured share of the non-excused time, in percent; method `time` only. |
| `credit_pct` | The month's [service credit](#service-credits) in percent of fees, three decimals. Empty without a schedule or a judgement. |
| `credit_steps` | Started steps below the target. Empty without a schedule or a judgement. |

## Maintenance

What a status page [maintenance](/docs/reference/maintenance) does to the figure depends on each monitor's [maintenance setting](/docs/reference/maintenance#checks-during-maintenance):

- **Pause checks** (default): cloud regions do not check the monitor while the maintenance is active. That time is left out of both sides of the fraction. It never counts as downtime, whatever happened during it.
- **Keep checking without alerting:** checks run as usual and their real outcome counts. A failure during the maintenance counts against uptime like any other time; it just does not change the monitor's status, open an incident or notify anyone.

To leave a maintenance out of the figure for such a monitor, excuse it: **Excuse** next to a maintenance window on the reporting page opens the [excused window](#excused-windows) dialog with its times and title prefilled. Edit the times first if the maintenance overran and the overrun should count. Excusing is a separate step on purpose, so an overrun can be left to count. Excusing a maintenance for a monitor whose checks pause is allowed but changes nothing, since that time is not counted anyway; the dialog says so.

The reporting page lists, per month, the maintenance windows that touched its monitors, found through the status page components they are linked to. It also shows for each monitor whether its checks pause or continue, with a link to [change the setting](https://app.openstatus.dev/monitors/_/edit#maintenance).
