A maintenance window is a scheduled period during which you expect planned disruption to one or more services — a database upgrade, a deployment, or infrastructure work. Announcing it ahead of time lets you communicate the disruption to your users instead of letting your status page register it as an unexpected outage.

A maintenance belongs to a single status page and targets one or more of that page's components — monitor-linked or static.

## Behaviour

While a maintenance window is active (the current time is between `from` and `to`):

- The affected components display the **Under Maintenance** (info) status on the status page.
- A higher-priority event overrides it: an active incident (error) or an unresolved status report (degraded) takes precedence, so the component shows that status instead. Maintenance only outranks the default operational status.
- The maintenance is reflected in the historical status bars for the days it overlaps.

The monitors behind the affected components pause while it is active, so the window is absent from their uptime, unless the maintenance announces a [maintenance window](#maintenance-window), which then decides instead. See [Checks during maintenance](#checks-during-maintenance).

When a maintenance is created, status page subscribers can be notified that it has been scheduled (see [Notify](#notify)). Updating a maintenance never re-notifies.

## Configuration and properties

### Title

**Type:** String (required)
**Length:** 1–256 characters

A short, human-readable name for the maintenance window.

**Example:** `"Database Upgrade"`

### Message

**Type:** String (required)

The text shown to users, explaining what is happening and the expected impact. On create it is posted as the first [update](#updates); on read it is the message of the newest update; on update it rewrites the newest update. New timeline entries are added through the update endpoints, not through this field.

**Example:** `"Upgrading our database to improve performance. Brief interruptions may occur."`

### From

**Type:** Datetime (required)
**Format:** RFC 3339 / ISO 8601 (e.g., `2026-01-20T02:00:00Z`)

When the maintenance window starts.

### To

**Type:** Datetime (required)
**Format:** RFC 3339 / ISO 8601 (e.g., `2026-01-20T04:00:00Z`)

When the maintenance window ends. Must be later than `from`.

### Status page

**Type:** Integer (required)

The id of the status page this maintenance belongs to. A maintenance is scoped to exactly one status page.

### Affected components

**Type:** Array of integers (optional)
**Default:** `[]`

The ids of the page components that should display the Under Maintenance status during the window. Each component must belong to the status page referenced above, and can be either a monitor-linked or a static component.

In the v1 REST API these are passed as `monitorIds`, which accepts monitor components only and is retained for backward compatibility. Static components can be targeted through the dashboard.

### Maintenance window

**Type:** Integer (optional, dashboard only)

The [maintenance window](#checks-during-maintenance) this maintenance announces. Set by **Announce on status page** on a window; a maintenance created on the status page has none. While set, the maintenance's `from` and `to` follow the window and cannot be changed on the maintenance itself, and the window alone decides what happens to checks. Internal: never shown on the status page, in feeds or in subscriber emails.

### Notify

**Type:** Boolean (optional)
**Default:** `false`

A one-time flag evaluated at creation time — it is **not** stored on the maintenance record and cannot be read back. When set, status page subscribers are notified that the maintenance has been scheduled.

The v1 REST API does not expose this flag; it notifies subscribers automatically when a maintenance is created on a page whose workspace has subscribers enabled.

## Updates

A maintenance is a timeline of dated notes. The first one is the announcement written at creation, later ones track progress, for example "Work started", "Taking longer than expected" or "Completed early". Each update has:

- **Message** — String (required). The note shown on the status page.
- **Date** — Datetime (optional). When the note applies. Defaults to the time it is posted.
- **Notify** — Boolean (optional, write-only). Sends the note to status page subscribers.

A maintenance always keeps at least one update: deleting the last one is rejected; delete the maintenance instead. Reads return them newest-first under `updates` (RPC, agent tools) or `maintenanceUpdates` (status page JSON). The public status page, feeds and Markdown render the updates in order, oldest first on the page.

## Checks during maintenance

Two things can put a monitor in maintenance:

- **A maintenance window** on the monitor (dashboard, monitor's **Maintenance** tab). It needs no status page and has a setting:
  - **Pause checks** (default): cloud regions do not check the monitor at all. The window is absent from both sides of its uptime and can never count as downtime, whatever happened during it.
  - **Keep checking**: cloud checks run and are stored as usual, with their real outcome, so failures during the window count against uptime. The monitor's status does not change, no monitor incident opens and no notification is sent. When the window ends, normal behaviour resumes with the next check: a failure that is still there then opens its incident and notifies.
- **A status page maintenance** that does not announce a window pauses the monitors behind its affected components.

**Announce on status page** on a window creates a maintenance that announces it. That maintenance changes nothing by itself: its times follow the window and the window's setting applies to the window's monitors. To announce work without losing measured time, create a window set to **Keep checking** and announce it. A window cannot be deleted while a maintenance announces it; unlink the maintenance (it then pauses its components' monitors again) or delete it first.

When several windows or maintenances cover a monitor at once, **Keep checking** wins over **Pause checks**, so measured time is never lost.

Private locations keep checking during any maintenance and ignore status changes while it is active. Heartbeat monitors are never evaluated during maintenance.

For what this means for a monthly uptime target, see the [monitor reporting reference](/docs/reference/monitor-reporting#maintenance).

## Relationships

- **Status page** — a maintenance is tied to a single page. Deleting the page deletes its maintenance windows.
- **Page components** — a maintenance can affect multiple components (monitor-linked or static), and a component can be covered by multiple (including overlapping) maintenance windows.
