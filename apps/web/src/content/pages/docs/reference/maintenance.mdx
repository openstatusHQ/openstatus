A maintenance window is a scheduled period during which you expect planned disruption to one or more services — a database upgrade, a deployment, or infrastructure work. Announcing it ahead of time lets you communicate the disruption to your users instead of letting your status page register it as an unexpected outage.

openstatus has two maintenance resources, with one rule between them: **only maintenance windows affect checks; status page maintenances communicate.**

- A **status page maintenance**, which this page covers first, belongs to a single status page and targets one or more of that page's components — monitor-linked or static. It is what your users see.
- A **maintenance window** belongs to one or more monitors and needs no status page. It decides whether their checks pause or keep running; see [Checks during maintenance](#checks-during-maintenance).

The two meet in one of two ways. A status page maintenance whose components are backed by monitors gets a maintenance window automatically, which pauses those monitors for its duration. Or it announces a window you created yourself, and then changes no checks at all.

## Behaviour

While a maintenance window is active (the current time is between `from` and `to`):

- The affected components display the **Under Maintenance** (info) status on the status page.
- A higher-priority event overrides it: an active incident (error) or an unresolved status report (degraded) takes precedence, so the component shows that status instead. Maintenance only outranks the default operational status.
- The maintenance is reflected in the historical status bars for the days it overlaps.

The monitors behind the affected components pause while it is active, through the [maintenance window](#maintenance-window) openstatus creates for it, so that time is absent from their uptime. A maintenance that announces a window you created pauses nothing itself. See [Checks during maintenance](#checks-during-maintenance).

When a maintenance is created, status page subscribers can be notified that it has been scheduled (see [Notify](#notify)). Updating a maintenance never re-notifies.

## Configuration and properties

### Title

**Type:** String (required)
**Length:** 1–256 characters

A short, human-readable name for the maintenance window.

**Example:** `"Database Upgrade"`

### Message

**Type:** String (required)

The text shown to users, explaining what is happening and the expected impact. On create it is posted as the first [update](#updates); on read it is the message of the newest update; on update it rewrites the newest update. New timeline entries are added through the update endpoints, not through this field.

**Example:** `"Upgrading our database to improve performance. Brief interruptions may occur."`

### From

**Type:** Datetime (required)
**Format:** RFC 3339 / ISO 8601 (e.g., `2026-01-20T02:00:00Z`)

When the maintenance window starts.

### To

**Type:** Datetime (required)
**Format:** RFC 3339 / ISO 8601 (e.g., `2026-01-20T04:00:00Z`)

When the maintenance window ends. Must be later than `from`.

### Status page

**Type:** Integer (required)

The id of the status page this maintenance belongs to. A maintenance is scoped to exactly one status page.

### Affected components

**Type:** Array of integers (optional)
**Default:** `[]`

The ids of the page components that should display the Under Maintenance status during the window. Each component must belong to the status page referenced above, and can be either a monitor-linked or a static component.

In the v1 REST API these are passed as `monitorIds`, which accepts monitor components only and is retained for backward compatibility. Static components can be targeted through the dashboard.

### Maintenance window

**Type:** Integer (read-only in the API; linked and unlinked in the dashboard)

The [maintenance window](#checks-during-maintenance) that carries this maintenance's effect on checks. It is one of:

- **Its own window**, created automatically when at least one affected component is backed by a monitor. It pauses those monitors from `from` to `to` and follows the maintenance: changing the times, the title or the components changes the window, and removing the last monitor-backed component removes it. It is listed under **Maintenance windows** as *From status page maintenance* and can only be changed through the maintenance.
- **A window you created**, which the maintenance announces. Set by **Announce on status page** on a window, or by **Link to a maintenance window** on the maintenance. That window alone decides the checks; the maintenance's components change none.
- **None**, when no affected component has a monitor and no window is announced. No checks change.

`from` and `to` always belong to the maintenance: they are the public times. For an announced window they start as the window's times and can be changed freely, for example to publish a wider range than the work itself; editing the window later does not move them. The dashboard shows both.

Internal: never shown on the status page, in feeds or in subscriber emails.

### Notify

**Type:** Boolean (optional)
**Default:** `false`

A one-time flag evaluated at creation time — it is **not** stored on the maintenance record and cannot be read back. When set, status page subscribers are notified that the maintenance has been scheduled.

The v1 REST API does not expose this flag; it notifies subscribers automatically when a maintenance is created on a page whose workspace has subscribers enabled.

## Updates

A maintenance is a timeline of dated notes. The first one is the announcement written at creation, later ones track progress, for example "Work started", "Taking longer than expected" or "Completed early". Each update has:

- **Message** — String (required). The note shown on the status page.
- **Date** — Datetime (optional). When the note applies. Defaults to the time it is posted.
- **Notify** — Boolean (optional, write-only). Sends the note to status page subscribers.

A maintenance always keeps at least one update: deleting the last one is rejected; delete the maintenance instead. Reads return them newest-first under `updates` (RPC, agent tools) or `maintenanceUpdates` (status page JSON). The public status page, feeds and Markdown render the updates in order, oldest first on the page.

## Checks during maintenance

Only a **maintenance window** puts a monitor in maintenance. A window has a setting:

- **Pause checks** (default): cloud regions do not check the monitor at all. The window is absent from both sides of its uptime and can never count as downtime, whatever happened during it.
- **Keep checking**: cloud checks run and are stored as usual, with their real outcome, so failures during the window count against uptime. The monitor's status does not change, no monitor incident opens and no notification is sent. When the window ends, normal behaviour resumes with the next check: a failure that is still there then opens its incident and notifies.

A window comes from one of two places:

- **You create it** on the monitor (dashboard, **Maintenance windows** or the monitor's **Maintenance** tab). It needs no status page.
- **A status page maintenance creates it.** A maintenance with monitor-backed components gets a window set to **Pause checks**, with the maintenance's times and the monitors behind those components. This is how a maintenance scheduled on a status page, through the API or by an import pauses its monitors. The window exists only as long as the maintenance does and cannot be edited, ended or deleted by itself.

### Announcing a window

**Announce on status page** on a window you created publishes a status page maintenance for it. The announcement is communication only:

- The window's setting and monitors decide the checks. The announcement's components are what the status page shows as Under Maintenance and change no checks.
- The announcement's `from` and `to` are prefilled with the window's and stay independent. Moving or ending the window does not change what the status page says; update the announcement yourself.

To announce work without losing measured time, create a window set to **Keep checking** and announce it.

**Link to a maintenance window** on an existing maintenance does the same after the fact: the maintenance stops pausing through its own window, which is removed, and the linked window takes over. **Unlink** reverses it: the maintenance gets its own pause window back if it has monitor-backed components.

### Deleting

- Deleting a status page maintenance, or its status page, removes the window that was created for it. A window it only announced stays.
- A window you created cannot be deleted while a maintenance announces it; unlink or delete the announcement first.
- Removing a component from a status page, or deleting its monitor, takes that monitor out of the windows created for the page's maintenances.

### Rules that hold for every window

**No alerts are sent during any maintenance window**, whichever setting applies: a check that ran inside the window never changes the monitor's status, opens an incident or notifies anyone. A check that ran before the window still counts, even if its result arrives a little later.

When several windows cover a monitor at once, **Keep checking** wins over **Pause checks**, so measured time is never lost.

Private locations keep checking during any window and ignore status changes while it is active. Heartbeat monitors are never evaluated during a window.

For what this means for a monthly uptime target, see the [uptime target reference](/docs/reference/uptime-target#maintenance).

## Relationships

- **Status page** — a maintenance is tied to a single page. Deleting the page deletes its maintenances and the windows created for them.
- **Maintenance window** — a maintenance has at most one: its own, or one it announces. A window you created can be announced by several maintenances, one per status page from the dashboard.
- **Page components** — a maintenance can affect multiple components (monitor-linked or static), and a component can be covered by multiple (including overlapping) maintenance windows.
