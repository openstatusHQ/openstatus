An uptime target is a named availability commitment: a monthly uptime percentage applied to a set of monitors. openstatus judges every monitor in the uptime target on its own, month by month, and seals each month once it is over, so the result you show a customer no longer changes.

Find them in the dashboard under [**Reports**](https://app.openstatus.dev/reports). Uptime targets are included in the Pro and Scale plans.

## Properties

| Property | Description |
|---|---|
| Name | Required. Shown in the list, on the uptime target's page, in the export and the email. |
| Monthly uptime target | A percentage with up to three decimals, for example `99.9`. Presets: `99`, `99.5`, `99.9`, `99.95`, `99.99`. The form shows how much downtime the target allows in a 30-day month. One percentage per uptime target, the same for every monitor in it. |
| Count slow responses as downtime | Off by default. See [strict mode](#strict-mode). |
| Time zone | `UTC` by default. The zone the uptime target's months start and end in. It can be changed only until the first month is sealed. |
| Monitors | The monitors the uptime target covers. A monitor can be in several uptime targets. |

Owners and admins can create, edit, archive and delete uptime targets, and add or remove [excused windows](#excused-windows). Every workspace member can view them and download the export. Each change is recorded in the audit log, with the values before and after an edit.

Uptime targets are managed in the dashboard only. They are not available over the API, the CLI or the MCP server.

### Eligible monitors

An uptime target judges run verdicts (see [method](#method)), so it accepts only monitors that produce them:

- **Accepted:** [HTTP](/docs/reference/http-monitor), [TCP](/docs/reference/tcp-monitor), [DNS](/docs/reference/dns-monitor), [ICMP](/docs/reference/icmp-monitor) and [gRPC](/docs/reference/grpc-monitor) monitors that check from at least one cloud region.
- **Rejected:** heartbeat monitors, and monitors that run from [private locations](/docs/reference/private-location) only. The form names the monitor and the reason.

## What is judged

One monitor, one calendar month in the uptime target's time zone. There is no combined figure across an uptime target's monitors: an uptime target with three monitors produces three results per month, each met or missed against the same target.

Months start and end at local midnight in the uptime target's [time zone](#properties), on the page, in the export, when sealed and in the email. With the default `UTC`, a failed run at 23:30 UTC on October 31 belongs to October.

### Method

The figure weighs **time**, not requests. A run is one scheduled check of a monitor, carried out by every cloud region the monitor is set to. Each run gets one verdict from the regions that reported it:

| Verdict | When |
|---|---|
| Failed | At least half of the reporting regions failed. |
| Slow | Not failed, and at least half of the reporting regions were slow or failed. |
| OK | Otherwise. |

So one slow or failing region out of three is a normal run. Choosing the regions is up to you: regions close to your users make the majority mean something.

A verdict stands until the next run, so each run weighs the time up to the next one, and a change of check frequency mid-month changes nothing. When the gap between two runs is more than twice the longer of the gaps before and after it, the earlier verdict covers only that longer gap and the rest of the gap is **unmeasured**. The time before the first run and after the last follow the same rule. Unmeasured time is neither up nor down: paused monitors, [paused checks during a maintenance](#maintenance) and scheduler outages leave the month instead of counting against it. **Coverage** is the share of the month's non-excused time that was measured.

On-demand checks and private locations never count. They are requests outside the schedule, or outside the cloud regions.

### Monthly uptime

```
measured = OK time + slow time + failed time      (excused time cut out)
down     = failed time + slow time                in strict mode
down     = failed time                            otherwise
uptime   = (measured − down) / measured
```

Excused time is the time inside the uptime target's [excused windows](#excused-windows), cut out at the millisecond. It drops from both sides of the fraction.

- A month is **met** when its uptime is at or above the target. A month exactly at the target is met. The comparison is exact, on whole milliseconds.
- Uptime is shown with three decimals, **rounded down**, so a missed month never displays as its target.
- A month without measured time has no judgement. It shows an em dash (`—`): never 100%, never a miss. The same holds for a month whose time was all excused.

### Strict mode

With **Count slow responses as downtime** on, slow time counts as down instead of up. A check is slow when it takes longer than its own monitor's degraded threshold (for example the HTTP monitor's [degraded](/docs/reference/http-monitor#degraded) setting), as recorded when it ran. A monitor without a degraded threshold is never slow, so strict mode changes nothing for it; the form flags such monitors.

## Month states

The uptime target's page shows a table of its monitors against the last 12 or 24 months, plus the running month. Each cell is in one of these states, the first that applies:

| State | When | Figures from | Target and strict mode |
|---|---|---|---|
| Sealed | The month was sealed for this monitor and uptime target. | The times stored at sealing. | The ones stored at sealing. |
| Preview | The previous month, over and not sealed yet (at most 45 days after it began). | Its checks. | The ones that will seal it. |
| Live, provisional | The running month. | Its checks so far. | The ones in effect this month. |
| None | Any other month: before the uptime target existed or the monitor joined it, or never sealed. | — | — |

- Sealed cells are filled; preview cells have a dashed border; live cells use a distinct tone. Hover a sealed cell for its seal date and stored terms.
- Months are only judged from their own checks or their seal. A month older than the previous one that was never sealed has no figure.
- A live month below target is a miss in progress, not a result. If recent checks cannot be loaded, the page still renders and says the recent weeks may be incomplete.

### Month detail

Select any month cell to open that monitor's month in a side sheet. The month is kept in the address (`?monitor=…&month=YYYY-MM`), so a link opens the same month. Cells without data cannot be opened.

| Part | Shows |
|---|---|
| Uptime | The month's figure and its coverage. A live month reads **So far**. |
| Budget left | The downtime the target allows in the month minus the time already counted as down. Negative once the month is over budget. |
| Budget left by day | A chart of the budget left at the end of each day, against an even burn from the full budget to zero, with each day's down and slow time as bars underneath. Where the budget ran out, a marker names the moment. A live month projects its current pace to the end of the month. |
| What used the budget | The month's down, slow, unmeasured and excused stretches, newest first, with how each was treated: counted, counted as up, excused or not measured. It lists the latest 50 and says how many older ones there are. |

- The header says whether the month is sealed, a preview or live.
- A sealed month lists its stretches from the monitor's [stored checks](#sealing), cut by the excused windows and the strict setting it was sealed with, so what used the budget stays visible after the raw checks expire.
- **Excuse a window** opens the [excused window](#excused-windows) dialog prefilled with the latest counted stretch. It is offered for the live and the preview month only, since older and sealed months are locked.

### Sealing

Sealing works in two steps, both run by a daily task.

First, the checks of every monitor in an uptime target that is not archived are stored a day behind, as its up, slow, down and unmeasured stretches. They are stored once per monitor, so a monitor in two uptime targets is measured once and both seal from the same record. A monitor that is in no uptime target is not stored; when it joins one, its record starts with the checks still kept, at most 40 days back.

Then the previous month is sealed from that store. For each monitor in an uptime target the task seals the month when all of these hold:

- At least 72 hours have passed since the month ended in the uptime target's time zone, so an uptime target can still be corrected or deleted. Checks are kept for 45 days, so a month not sealed within 45 days of its start is never sealed.
- The uptime target, and the monitor's membership in it, both existed before the month ended. An uptime target created on November 5 is first sealed for November, never for October.
- The monitor's checks are stored up to the end of the month. If not, the next run tries again.
- The uptime target is not archived, the monitor is not deleted and the workspace's plan includes uptime targets.

Sealing stores the measured, down, excused and unmeasured time, the excused windows that applied, and the target and the strict setting of that moment. It never changes afterwards. The stretches behind the figure stay in the monitor's stored checks. A month whose time was all excused is sealed without a judgement and keeps its windows. A month that is still unsealed when it stops being the previous month shows no figure.

### Missed months

"The last 12 months" always means the twelve complete months before the current one.

- **Per monitor:** how many of those months it missed.
- **Per uptime target:** how many of those months had at least one monitor miss. This is the number a "three missed months in twelve" clause reads.

Both count sealed and preview months, and say how many of the misses are previews. Live months never count. The **Reports** list shows the same twelve months as a strip per uptime target: a month is missed when any monitor missed it, met when at least one monitor was judged and none missed, and empty otherwise.

When a sealed month misses its target, the workspace owners get one email per uptime target and month, listing the monitors that missed and linking to the uptime target.

## Excused windows

An excused window is a stretch of time that does not count for the monitors it names: a planned maintenance, an outage caused by the customer, a provider failure your contract excludes. Add one from the **Excused downtime** section of the uptime target's page with **Add window**.

| Field | Description |
|---|---|
| From, To | The window, at most 7 days long. Entered in your browser's timezone; the list shows windows in UTC. |
| Kind | `Maintenance`, `Emergency`, `Third party`, `Customer caused`, `Force majeure` or `Other`. A label for the record; it changes nothing in the calculation. |
| Reason | Required. Shown in the list and kept with the sealed month. |
| Monitors | At least one monitor of the uptime target. Every member is selected by default; excusing from a maintenance selects that maintenance's monitors. |

- A window applies only to the monitors it names. A monitor added to the uptime target later is not covered by existing windows.
- Runs inside it are left out of both sides of the month: neither up nor down.
- Overlapping windows excuse a run once.
- A window across a month boundary is split there. Each month drops only its own part.
- Windows can only be added or removed in the current and the previous month, and only while no month they touch is sealed. A sealed month records the windows that applied, so its figure never changes. Locked windows show a lock icon.
- The add dialog shows when the last window of the same kind started and how many of the last two complete months had a miss. It refuses nothing on that account: contract rules about which windows qualify, such as notice periods or weekly limits, are not checked.
- Adding and removing a window are recorded in the audit log.

## Editing, archiving and deleting

- A new target or strict setting applies at once to the running month and to a previous month that is not sealed yet. Sealed months keep the terms they were sealed with.
- Adding a monitor judges it from the moment it joined; earlier months show none.
- Removing a monitor keeps its sealed months. They are hidden until the monitor is added back.
- Deleting a monitor removes it from every uptime target.
- An uptime target without a sealed month can be deleted.
- An uptime target with a sealed month can only be archived: it becomes read-only, seals no further months and leaves the default list. Its sealed months stay on record. The **Archived** tab still shows it.

## Export

The **Export** button on an uptime target's page downloads its months as a CSV file, one row per monitor and month. This is the file to send to a customer or auditor.

- Pick a range of months. The default is the last 12 complete months; a file covers at most 60.
- Live months are left out unless you tick **Include live months**. They are then marked `live (provisional)`.
- The figures equal the ones on the page. Sealed rows carry the target and strict setting they were sealed with.

The first line states the method. The second says when the file was generated, which time zone the calendar months are in, that excused time is left out of both sides, that durations are in milliseconds, and that uptime is floored to three decimals. Then the columns:

| Column | Description |
|---|---|
| `uptime_target` | Uptime target name. |
| `target` | Target in percent, for example `99.900`. |
| `strict` | `yes` or `no`. |
| `monitor_id`, `monitor_name`, `monitor_url` | The monitor. |
| `month` | `YYYY-MM`. |
| `state` | `sealed`, `preview`, `live (provisional)` or `none`. |
| `uptime` | Percent, floored to three decimals. Empty when nothing was measured, or when all of it was excused. |
| `met` | `yes`, `no`, or empty when nothing was measured or all of it was excused. |
| `sealed_at` | ISO timestamp, sealed rows only. |
| `time_zone` | The zone the month is in. |
| `measured_ms` | Time with a check verdict, outside the [excused windows](#excused-windows), in milliseconds. See [method](#method). |
| `down_ms` | The part of the measured time that counts against the target, in milliseconds. |
| `excused_ms` | Time inside the excused windows, left out of both sides of the uptime, in milliseconds. `0` without windows. |
| `unmeasured_ms` | Time outside the excused windows without a check verdict, in milliseconds. |
| `coverage` | Measured share of the non-excused time, in percent. |

## Maintenance

What a maintenance does to the figure depends on [what puts the monitor in maintenance](/docs/reference/maintenance#checks-during-maintenance): a maintenance window's setting, or pausing for a status page maintenance that announces no window:

- **Pause checks** (default): cloud regions do not check the monitor while it is active. That time is left out of both sides of the fraction. It never counts as downtime, whatever happened during it.
- **Keep checking:** checks run as usual and their real outcome counts. A failure during the maintenance counts against uptime like any other time; it just does not change the monitor's status, open an incident or notify anyone.

To leave a maintenance out of the figure for such a monitor, excuse it: **Excuse** next to a maintenance window on the uptime target's page opens the [excused window](#excused-windows) dialog with its times and title prefilled. Edit the times first if the maintenance overran and the overrun should count. Excusing is a separate step on purpose, so an overrun can be left to count. Excusing a maintenance whose checks pause leaves the uptime unchanged, since that time is not counted anyway, but turns the unmeasured time into excused time, which raises coverage.

The uptime target's page lists, per month, the maintenance windows and status page maintenances that touched its monitors, each with its checks setting. A window and the maintenances announcing it are one row ("announced on …"). Excusing from a window records it with the excused window, and the dialog shows when the work was announced and how far ahead, as notice evidence; it refuses nothing.
