A playbook is a markdown document that says how your team does something: run an incident, write on the status page, schedule maintenance, write a postmortem. People read it during an incident, and the agent reads it when you ask how the team works and before it drafts public text.

A workspace has at most one playbook per slug. Playbooks are internal: nothing in them is published.

## Built-in playbooks

Four playbooks come with a default title, description and template:

| Slug | Covers | The agent reads it |
|---|---|---|
| `incident-response` | Severities, roles, steps, update cadence, escalation | When asked about the process, and before declaring an incident |
| `status-page` | Tone, what to say and never say, public names for internal systems | Before a status report, a status report update or a maintenance notice |
| `maintenance-windows` | What a window means, when it is scheduled, notice period, what the notice says | Before creating or changing a maintenance |
| `postmortem` | The sections of a postmortem and what goes in each | Before drafting a postmortem |

## Custom playbooks

For anything else your team does its own way, such as a database failover or a customer escalation, create a custom playbook: open [**Agents > Playbooks**](https://app.openstatus.dev/agents/playbooks#playbooks), click **Create playbook** and set a title, a slug and a description.

| Rule | |
|---|---|
| Slug | Lowercase letters, digits and single hyphens, up to 64 characters: `database-failover`. It cannot be changed later. |
| Title | Required |
| Description | Required. What the playbook covers. The agent is told the description and uses it to decide when to read the playbook, so say when it applies. |
| Limit | 20 custom playbooks per workspace |

A custom playbook has no template: it starts with its title as a heading. Deleting it removes it from the list.

## Writing a playbook

Open [**Agents > Playbooks**](https://app.openstatus.dev/agents/playbooks#playbooks) and pick a playbook.

- An empty playbook opens with a default template in the editor. Save it as is, or change it first. Nothing is stored until you save.
- **Reset template** puts the default text back in the editor.
- The text is markdown, up to 10,000 characters.
- Delete a playbook from the **⋯** menu on its row or next to its title. For a built-in playbook, the editor then opens on the template again.

### Title and description

Click the title or the description on the playbook's page to change it. The agent is told the description, so write it as what the playbook covers. Neither can be left empty.

| Field | Limit |
|---|---|
| Title | Up to 100 characters |
| Description | Up to 500 characters |

Any workspace member can write, change and delete playbooks.

## Variables

Write `{{name}}` in the text to add a variable, then set its value under **Variables** next to the editor. Use variables for the parts that change without the rule changing: a team name, a support address, a sign-off.

| Rule | |
|---|---|
| Name | Lowercase letters, digits and underscores, up to 64 characters: `{{support_email}}` |
| Value | Plain text, up to 500 characters |
| Saving | A value saves when you leave its field, once the saved text uses the variable. A variable you just typed is saved together with the text. |
| Unset | A variable without a value stays in the text as `{{name}}`, so the gap is visible to the reader and the agent |
| Limit | The 10,000 characters count the text with its variables filled in |

The preview shows the playbook with its variables filled in, each value marked as inline code.

## How the agent uses playbooks

The agent is told which playbooks exist and the description of each, not what they say. In Slack, the status report drafted right after an incident is declared always follows your `status-page` playbook. It reads one with `get_playbook` when you ask how the team does something, and before it drafts a status report, a maintenance notice or a postmortem. It is asked to read first; it is not forced to, so check a draft before you approve it.

- **Slack and the dashboard assistant**: the agent knows which playbooks are written and reads the relevant one on its own.
- **MCP**: the server instructions and the tool descriptions point the client's model at `list_playbooks` and `get_playbook`. See the [MCP server reference](/docs/reference/mcp-server#playbooks).

A playbook decides wording, structure, severity and process. It never overrides the approval step, and it cannot give the agent permissions it does not have.

### Slugs that are read by name

Two drafts load a playbook by its exact slug, without the agent choosing to:

| Slug | Read by |
|---|---|
| `postmortem` | The [postmortem draft](#postmortem-drafts) |
| `status-page` | The first status report Slack drafts after an incident is declared |

Rules for those two drafts only apply when they are written under these slugs. A custom playbook is never loaded this way: the agent reads it when its description fits the request, so a custom `our-postmortems` playbook does not shape the postmortem draft.

### Changing a playbook from the agent

Ask the agent to change a playbook and it calls `update_playbook`, which replaces its text; the same tool writes a built-in playbook for the first time. Ask for a new playbook of your own and it calls `create_playbook`, which needs a slug, a title and a description. Like every write, it needs your approval first. The agent cannot delete a playbook.

## Postmortem drafts

When a `postmortem` playbook exists, the [postmortem draft](/docs/reference/incident-management#postmortem) follows its structure in place of the seven default sections. The other rules stay: only the facts it was given, a UTC timeline, action items as a checklist. The draft's footer says it follows the team's playbook.

Without a `postmortem` playbook, drafts are unchanged.

## API

`PlaybookService` is part of the [API](https://api.openstatus.dev/openapi), under `/rpc/openstatus.playbook.v1.PlaybookService/`. Playbooks are addressed by slug.

| Method | What it does | Scope |
|---|---|---|
| `ListPlaybooks` | The playbooks the workspace has written, with title and description, without their text | `incidents:read` |
| `GetPlaybook` | One playbook: title, description, the text as written, its variable values and timestamps | `incidents:read` |
| `CreatePlaybook` | Creates a custom playbook: `slug`, `title`, `description` and `content` are required. Returns `failed_precondition` when the slug is taken and `invalid_argument` for a built-in slug | `incidents:write` |
| `UpdatePlaybook` | Replaces the text and variables of a playbook; `title` and `description` are optional. A built-in slug is created on its first write, a custom slug that does not exist returns `not_found` | `incidents:write` |
| `DeletePlaybook` | Removes the playbook of a slug | `incidents:write` |

```bash
curl https://api.openstatus.dev/rpc/openstatus.playbook.v1.PlaybookService/UpdatePlaybook \
  -H "x-openstatus-key: $OPENSTATUS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "slug": "status-page",
    "content": "Never promise a time for the fix. Sign off as {{team_name}}.",
    "variables": { "team_name": "The Acme platform team" }
  }'
```

`variables` replaces the stored values: a variable you leave out is unset, and names the text does not use are dropped. `title` and `description` are kept when you leave them out; an empty string is rejected. A built-in playbook stores the default title and description when it is first written, so they do not change afterwards unless you change them. `GetPlaybook` returns `not_found` when the workspace has no playbook for that slug.

## Audit log

Every write and delete is in the audit log with the member behind it and the full text before and after, whether it came from the dashboard, the agent or the API. A deleted playbook's text can be copied back from there.
