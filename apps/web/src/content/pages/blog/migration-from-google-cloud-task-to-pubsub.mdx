We recently moved the queue that triggers openstatus's uptime checks from Google Cloud Tasks to Pub/Sub. Our Google Cloud bill went from about 6.80€ a day to about 0.60€, or roughly 200€ to 20€ a month.

<Image src="/assets/posts/migration-from-google-cloud-task-to-pubsub/gcp-daily-cost.png" alt="Google Cloud daily cost in October 2026" />

The migration wasn't as smooth as the chart looks. We had to roll back our first attempt after 15 minutes because we were getting rate-limited by Tinybird. Then, a few days later, we noticed our latency numbers had jumped right after the switch.

In both cases, the issue was the same: Cloud Tasks had been smoothing our traffic for us, and we didn't realize how much we relied on it.

## Why we were on Cloud Tasks

When we started openstatus, our checkers ran on serverless platforms. We didn't want to miss a check, and a queue that pushes an HTTP request to wake up a function worked well for that. We also had Google startup credits, so it cost us nothing.

Since then, a few things changed:

- Our startup credits ran out, and at ~250M checks a month, Cloud Tasks was getting expensive.
- We rewrote our checker as a Go service running 24/7 on Fly, Koyeb, and Railway. There were no serverless functions left to wake up.
- Pushing checks over HTTP was awkward across multiple clouds. Each task hit a public URL with a region header (`fly-prefer-region`, `X-KOYEB-REGION-OVERRIDE`, `railway-region`). On Fly, if a request landed on a machine in the wrong region, it had to bounce it with `fly-replay`. It made much more sense for the machines to just pull their own work.

## How we set up Pub/Sub

### Topic layout and pricing

Cloud Tasks bills per operation ($0.40 per million). Pub/Sub bills per byte ($40 per TiB after the first 10 GiB), and our messages are small—about 650 bytes each.

Every check needs to run in a specific region. Our first idea was to use a single topic with a filtered subscription per region.

The catch is that Pub/Sub still bills you for messages that a subscription filter drops. Since we run in 27 regions, one topic with 27 filtered subscriptions means paying 27 times for every message: once for the region that runs the check, and 26 times for the regions that ignore it.

Here is what we estimated for the different setups:

| Setup | Estimated monthly cost |
| --- | --- |
| 1 topic, 27 filtered subscriptions (one per region) | ~$212 |
| 1 topic per region, filtered by periodicity | ~$41 |
| 1 topic per region, `30s` and the rest filtered | ~$17 |
| **2 topics per region, no filters** | **~$11** |

We went with 2 topics per region and no filters: `checker-<region>` and `checker-<region>-30s` (54 topics in total). Note that these numbers don't include GCP egress, which you still pay when your workers run outside GCP like ours do.

Having separate topics per region is also nice for isolation. If one region goes down or falls behind, its backlog stays in its own subscription and doesn't affect the others.

### Handling 30-second checks without delayed delivery

Why have a separate `-30s` topic if we aren't using filters? Because Pub/Sub doesn't support delayed delivery.

Our scheduler cron runs once a minute. A 30-second monitor needs to run twice per minute: once right away, and once 30 seconds later. With Cloud Tasks, we scheduled the second run using `scheduleTime`. With Pub/Sub, we publish both messages at the start of the minute, put a `cronTimestamp` 30 seconds in the future on the second one, and let the checker sleep until it's time to run.

If those sleeping messages shared a subscription with the 1m, 5m, and 10m checks, they would sit in `MaxOutstandingMessages` and block checks that need to run immediately. Giving `30s` its own topic lets us buffer up to 2,000 sleeping messages in memory while still capping active checks at 200 at a time. A message only takes one of the 200 slots after it wakes up.

### Acks, retries, and dead-lettering

From the queue's perspective, a check that fails because the target website is down is still a processed message, so we ack it. We only nack if we fail to save the result (for example, if Tinybird is down), and we ack and log messages that can never succeed, like invalid JSON. After 5 failed attempts, the message goes to a dead-letter topic.

Pub/Sub delivery is at-least-once and we don't deduplicate on the consumer side, so if a machine crashes mid-check we might record the same check twice. For uptime monitoring, an extra data point is fine compared to dropping a check.

## Shipping the migration

I used Claude Code a lot for this migration. It walked me through 17 design questions up front, and we split the work into four PRs so we could deploy each piece behind a flag:

1. [#2962](https://github.com/openstatusHQ/openstatus/pull/2962) moves the check logic out of the HTTP handlers.
2. [#2963](https://github.com/openstatusHQ/openstatus/pull/2963) adds the Pub/Sub consumer behind `PUBSUB_ENABLED`.
3. [#2964](https://github.com/openstatusHQ/openstatus/pull/2964) adds the publisher behind `CHECKER_TRANSPORT`.
4. [#2965](https://github.com/openstatusHQ/openstatus/pull/2965) removes the Cloud Tasks code (still in draft until we've been on Pub/Sub for two weeks).

Before switching the flag over, we ran a small script that checked every subscription had an active pull connection, sent one test check to all 54 topics, and waited for all 54 rows to show up in Tinybird. Everything passed, so we flipped `CHECKER_TRANSPORT=pubsub`.

Writing all of this by hand would have taken us weeks. With Claude Code, we agreed on the plan on October 21 and had it running in production on October 22.

## Issue 1: hitting Tinybird's rate limit

Before the migration, each checker sent its result directly to Tinybird—one HTTP POST per check. On Cloud Tasks, our ~5,700 checks per minute were spread out across the whole minute, which came out to about 95 requests per second to Tinybird. Tinybird's Events API has a hard limit of 100 requests per second per workspace, regardless of how many rows you send in a request. We had been sitting right below that limit without knowing it.

When we switched to Pub/Sub, all checkers pulled their batch at the start of the minute and ran at the same `cronTimestamp`. Instead of ~95 requests per second spread across the minute, we sent thousands of single-row writes in the first few seconds. Tinybird started returning 429s—about 1,400 of them in 90 seconds.

Our retry logic made it worse. When a write to Tinybird failed, the checker nacked the Pub/Sub message. Pub/Sub then redelivered the message, which ran the entire HTTP check again and tried to write to Tinybird again. Within 10 minutes, nacks went from 942 to ~12,000 per minute, and p99 ack latency hit 120 seconds.

We flipped the flag back to Cloud Tasks to stop the bleeding. Checks kept running the whole time and nothing hit the dead-letter topic. Our verification script hadn't caught this because sending one test check per topic only tests that the pipeline is connected, not how it behaves under load.

To fix it ([#2974](https://github.com/openstatusHQ/openstatus/pull/2974)), we added a batcher in the checker that implements our existing Tinybird `Client` interface:

- It buffers rows in memory per data source and flushes every 2 seconds (plus up to 1 second of random jitter), or when the buffer hits 5 MB.
- `SendEvent` waits until its batch is flushed before returning, so we still don't ack a Pub/Sub message until the row is written to Tinybird.
- If Tinybird returns a `429` or `5xx`, the batcher retries the write for up to 30 seconds (respecting `Retry-After`) without re-running the check itself.

That dropped our Tinybird traffic from thousands of single-row requests at the top of the minute to 17–50 batched requests per second across all regions. We deployed the fix and flipped the flag back to Pub/Sub the same afternoon.

## Issue 2: skewing our own latency measurements

Five days after the migration, we noticed a second problem that was much more annoying for a monitoring tool: our reported response times had gone up.

Cloud Tasks had a queue dispatch limit of 500 tasks per periodicity across all regions, which capped how many checks could start at the exact same moment. With Pub/Sub, every check for a given minute shared the same `cronTimestamp`, so a single checker machine could start up to 400 checks at the exact same millisecond.

Running hundreds of checks at once on a small VM caused their DNS lookups, TCP connections, and TLS handshakes to contend with each other. We were measuring latency that our own machines were creating.

Here is the P50 latency of one monitor over two weeks. You can see the jump on October 22 when we switched to Pub/Sub, and the drop back to normal on October 27 when we fixed it:

<Image src="/assets/posts/migration-from-google-cloud-task-to-pubsub/monitor-latency-p50.png" alt="P50 latency of one monitor from October 15 to 28, broken down by DNS, connect, TLS, TTFB, and transfer" />

The P50 jumped from ~50 ms to 100–300 ms, mostly in DNS, connect, and TLS time.

The fix ([#3010](https://github.com/openstatusHQ/openstatus/pull/3010)) was small. Instead of starting every check right at `cronTimestamp`, we add a deterministic delay between 0 and 2 seconds based on the hash of the monitor ID:

```go
// spread maps a monitor to a fixed delay in [0, window): the same monitor keeps
// the same offset every tick, so its checks stay one interval apart.
func spread(monitorID string, window time.Duration) time.Duration {
	if window <= 0 {
		return 0
	}
	h := fnv.New64a()
	h.Write([]byte(monitorID))

	return time.Duration(h.Sum64() % uint64(window))
}
```

We used a hash of the monitor ID instead of random jitter so that each monitor keeps the same offset every minute. If we used a random delay on each run, a 30-second monitor wouldn't run every 30 seconds anymore—the gap between two checks would drift from tick to tick.

## Takeaways

Overall we're really happy with the move. Paying ~20€/month instead of ~200€/month for the queue is a nice win, and pulling jobs from the workers is much simpler than bouncing HTTP requests across regions.

A few things we learned along the way:

- A push queue with dispatch limits smooths out your traffic for free. When you switch to pull consumers that wake up on the same cron tick, everything downstream (like Tinybird, or even the network stack on the worker VM) suddenly gets hit with bursts instead of a steady stream.
- Don't re-run the whole job when only the database write at the end failed. Retrying the Tinybird request locally before nacking the Pub/Sub message saved us from re-running thousands of HTTP checks during a rate limit.
- Watch out for subscription filter pricing on Pub/Sub. Putting the region in the topic name instead of filtering a single topic across 27 subscriptions made the difference between an ~$11 bill and a ~$212 bill.
