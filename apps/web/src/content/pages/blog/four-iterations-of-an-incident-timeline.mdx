## How I work with Claude

I'm riding Claude Code **raw**. No additional harness, no additional configuration. I like to keep my setup *simple*. It's easy to adapt, easy to switch, and it doesn't bind me to anything concrete. My terminal and settings look the same. I don't see me missing out on something. It evolves daily, and I'm sure I'm not using it to its full potential.

For deterministic tasks and fixes I use Claude Code remote. It spins up a VM and works isolated from the rest. When I'm hands-down on UI, or I want to test and navigate the codebase, I run Claude Code in the terminal. No worktrees either.

I am **obsessed** with proper `PLAN.md` files to `/loop` over once I'm afk. I keep plenty of Claude Code tabs open, grilling me on different ideas with Matt Pocock's goated grill-me skill. I rarely read those plans extensively, except when it's a collaboration with Thibault on a bigger-picture feature like incident response. We worked on that plan for a couple of days, with the idea spelled out for weeks before. Leave it, iterate the next day.

For dashboard work, Claude Code runs Playwright against my local dev server and screenshots the page after every change. That's how it checks its own work. I do the same from my side: a screenshot, the broken part **boxed in red**, one sentence. While a loop runs I go bouldering or for a walk. When I'm back I test on localhost, not on a preview link. The details only show up when you click through the real thing.

When it comes to UI/UX, I use Claude Design for a first feeling. Without steering it looks very *claudy*, gradients and italics, so most of the time it's purely for inspiration. I usually ask for three or four variations. For dashboard work we have our design system attached to both. Claude Design gets it as a project asset, so the mocks come out in our tokens, fonts and spacing instead of the default look. Claude Code gets it from the repo: shadcn primitives in `@openstatus/ui`, our own blocks on top, and `AGENTS.md` files that say to compose from those and never fork a primitive into an app. Neither can go off the rails too much. But both stay rather plain if I don't give enough details.

## Phase 1: from the plan

Phase 1 came from the plan. Thibault ran Claude through it and we were gifted 21 stacked PRs to merge. And it was good. **Really good.** The incidents page was feature-flagged to our workspace, and we merged one PR after the other. Thibault focused on the Slack app, me on the dashboard.

The UI came out raw, but the plan was followed *to the letter*. The two-column layout, the composer above the timeline, the properties on the right, the linked status report: all of that is in the spec. The buttons, badges and selects are ours, because the design system is in the repo and every session reads it. What was missing is **hierarchy**. Every event rendered the same: a left border, Type · Name · time, body text. Notes from Slack showed up as a bare "From Slack" link. It worked. It also looked like a *log file*.

## Phase 2: the right shape

I wanted a timeline with a visual distinction between event types. So I gave Claude Design a full-page screenshot of the current state and a few instructions:

> Focus on the content, not the layout. It's too flat. I want the events presented as a timeline. The inputs on the right should be transparent and only show their borders on hover or click.

A few minutes later:

<Image src="/assets/posts/four-iterations-of-an-incident-timeline/claude-design-mock.png" alt="The first Claude Design output: status pill and severity chip in the header, ghost inputs on the right, composer with a Set status to footer, icon discs on a rail" className="img-fit" />

**Miles better** than what we had. Ghost inputs on the right, the status change in the composer footer, icon discs on a rail, status chips. Next, I pasted a screenshot of it into Claude Code:

> This image is really good. Take your time and figure out how we get there. Be thoughtful about the React components, the way we do it in general: structure, compound components, cva. Don't commit, implement until you believe it's good. The components will be reused for status reports and maintenances later on.

What came back is the mock in our components, minus what didn't survive the data model. The incident ID went, our IDs are autoincrement and "INC-011" would be a lie. Affected monitors went, the incident doesn't link to monitors yet. Good for the first real update.

<Image src="/assets/posts/four-iterations-of-an-incident-timeline/02-timeline-rail.png" alt="Phase 2: a vertical rail with an icon per event type and status pills" className="img-fit" />

## Phase 3: avatars

A minor visual step. I kept the core Claude Design returned and focused on the user avatars.

> Notes show an author avatar and a type icon side by side. That's redundant. Make the avatar the timeline node, with the type as a small badge.

The first pass still rendered both. "There is redundancy, check again" fixed it. *More important than the avatars:* this phase migrated status reports and maintenances onto the same timeline, composer and aside components.

<Image src="/assets/posts/four-iterations-of-an-incident-timeline/03-avatars.png" alt="Phase 3: the author avatar is the timeline node, the type a small badge" className="img-fit" />

## Phase 4: hierarchy

The last big push. I shared the current visuals on X and Marc from [Papermark](https://www.papermark.com) pointed me to [Linear](https://linear.app). I've been using Linear and I know their great timeline. Which just shows: sometimes you need a *small nudge* in the right direction. It was the final piece of the puzzle.

I stared a while at their timeline. What makes it so good, and why don't I get bored watching it? It's the **hierarchy of events**. Comments are *loud*, everything else is *quiet*. You read the conversation and skim the plumbing. And because the shape repeats on every issue, you learn the workflow without anyone explaining it. Our timeline had no levels, so every event asked for the same attention.

It was clear: **we need it too**. I gave Claude Design some Linear screenshots and a few of our current designs:

> Design our timelines closer to Linear. The composer is always the first thing, and the activity is newest first.

<Image src="/assets/posts/four-iterations-of-an-incident-timeline/claude-design-linear-mock.png" alt="The second Claude Design output: composer on top, notes and status changes as cards, system events as one-liners" className="img-fit" />

I could have given Claude Code the screenshots straight up and it would have nailed it, I'm pretty sure. Then the loop:

> /loop and improve our activity timeline across incidents, maintenances and status reports, a bit à la Linear like the screenshots. Don't commit, implement and rework over time. Keep everything on the same compound components.

Then one observation at a time, each with a boxed screenshot:

> Feels too crowded.

> Linear doesn't highlight simple event names in the timeline, only comments. Do the same.

What changed:

- Notes and status changes became cards written as sentences: Thibault marked Resolved.
- System events collapsed into one-liners: linked status report #3473.
- The composer got subtle actions in its footer. No border, no descriptive text.
- The "Post public update" button in the aside took way too much visual space. The linked status report is now one row in the label-value properties, actions behind a menu.

<Image src="/assets/posts/four-iterations-of-an-incident-timeline/04-hierarchy.png" alt="Phase 4: notes and status changes as cards, system events as one-liners" className="img-fit" />

The timeline is less tall and less loud because it has levels. The important stuff reads like a *story*.

I'm still feeling like a **meat proxy**. I manually juggle between Claude Code, Claude Design and localhost, adding instructions and being a mostly useless human in the loop. Useless in the typing sense only. I'm in *full control* of what happens and what doesn't: what gets built, what gets dropped, what ships. Four phases, a handful of prompts that said what was wrong rather than what to build, and the timeline is where I want it.
